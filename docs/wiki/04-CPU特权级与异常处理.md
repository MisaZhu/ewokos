# 04 CPU 特权级与异常处理

> 本章目标：理解 ARM 的 4 个特权级（EL0~EL3），看懂 EwokOS 启动时
> 如何切换特权级，理解"异常"机制与异常向量表，明白用户程序如何被"管住"。
> 本章术语（EL0~EL3/eret/VBAR/ELR/SPSR…）见 [附录·术语表](99-术语表-专业名词速查.md)。

## 4.1 为什么需要特权级

上一章的裸机程序可以随意读写任何内存和任何设备。如果同时跑着 10 个程序，
任何一个程序写错地址都会把其他程序甚至硬件搞坏。

ARMv8 CPU 提供了 4 个**异常级别（Exception Level）**，级别越高权力越大：

```
┌────────────────────────────────────────────┐
│ EL3  Secure Monitor（安全固件，我们不用）      │
│ EL2  Hypervisor（虚拟化，启动时短暂路过）      │
│ EL1  OS 内核 ← EwokOS 内核运行在这里          │
│ EL0  用户态 ← 所有用户进程（shell、应用）      │
└────────────────────────────────────────────┘
```

规则很简单：
- **EL0 的程序不能执行特权指令**（如修改页表、操作中断），执行即触发异常；
- **EL0 的程序不能访问被保护的资源**（内核内存、设备寄存器），访问即触发异常；
- 只有 EL1 的内核能配置这些保护规则（通过页表和系统寄存器）。

"异常（Exception）"是个统称，包含四类事件：

| 类型 | 例子 |
|------|------|
| 中断（IRQ） | 定时器到期、键盘按键、SD 卡读完数据（第 06 章） |
| 同步异常 | 非法内存访问、执行特权指令 |
| 系统调用（SVC） | 用户程序主动请求内核服务（第 08 章） |
| 系统错误（SError） | 总线错误等 |

**异常发生时，CPU 自动做三件事**：保存返回地址、切到更高级别、
跳转到"异常向量表"中对应的处理入口。内核的全部权力就建立在这个机制上。

## 4.2 EwokOS 的启动：从 EL2 降到 EL1

树莓派 3B/4B 上电时，CPU 处在 **EL2**（虚拟化层）。操作系统内核应该跑在
EL1，所以 EwokOS 启动代码要做的第一件事就是"降级"。

看 [boot.S](../../kernel/platform/aarch64/arch/v8/boot.S) 开头（带注释版）：

```asm
__entry:
    msr DAIFSet, #0xf        ; 屏蔽全部异常和中断（现在还不能被打断）

    mrs x0, CurrentEL        ; 读当前特权级
    cmp x0, #4               ; EL2 的编码是 4（左移了 2 位）
    beq __el1_entry          ; 已经在 EL1 就直接走

    ; --- 当前在 EL2，做降级准备 ---
    mov x0, #1
    mov x1, xzr
    bfi x1, x0, #31, #1      ; HCR_EL2.RW=1：EL1 使用 64 位模式
    orr x1, x1, #0x2
    msr HCR_EL2, x1          ; 写虚拟化控制寄存器

    mov x0, #0x3c5
    msr SPSR_EL2, x0         ; 设定"返回后"的状态：EL1、关中断
    adr x2, __el1_entry
    msr ELR_EL2, x2          ; 设定"返回地址"为 EL1 入口
    eret                     ; ★异常返回：跳到 ELR_EL2，特权级降为 EL1
```

关键概念：
- `msr` / `mrs`：写 / 读系统寄存器；
- `eret`（Exception Return）：不是普通跳转，它会把特权级切换成
  `SPSR` 里保存的级别，并跳到 `ELR` 保存的地址。降级就是"伪造一次异常返回"。

降到 EL1 后，代码继续做这些准备工作：

```asm
__el1_entry:
    ; 关闭对齐检查、关闭 MMU（此刻还没有页表）
    mrs x0, SCTLR_EL1
    bic x0, x0, #1
    msr SCTLR_EL1, x0

    ; 允许使用浮点/NEON（否则访问会触发异常）
    mrs x0, CPACR_EL1
    mov x1, #0x3
    bfi x0, x1, #20, #2
    msr CPACR_EL1, x0

    msr spsel, #0x1          ; 使用 EL1 专用栈
    adr x0, #_svc_start_stack
    mov sp, x0               ; 设置栈

    bl _boot_start           ; 进入 C：建立启动页表、打开 MMU（第 05 章）

    ; 多核：从核去 slave_core，主核继续
    ldr x1, =_kernel_entry_c ; 进入内核 C 入口
    br x1
```

注意 `SCTLR_EL1` 这个系统寄存器——它是 EL1 的总开关，里面的
**M 位控制 MMU 开或关**，第 05 章打开它。

## 4.3 异常向量表：异常的"总机"

内核运行起来后，随时可能被异常打断（定时器响了、用户程序访存出错、
用户程序发起系统调用……）。CPU 被打断后跳去哪？跳去 **VBAR_EL1**
（Vector Base Address Register）指向的**异常向量表**。

AArch64 的向量表有 **16 个入口**（4 类来源 × 4 类异常），每个入口间隔 128 字节：

```
来源\类型      同步异常      IRQ        FIQ       SError
────────────────────────────────────────────────────────
当前 EL，用SP_EL0   +0x000   +0x080   +0x100   +0x180
当前 EL，用SP_ELx   +0x200   +0x280   +0x300   +0x380
来自低级别(如EL0)   +0x400   +0x480   +0x500   +0x580  ← 用户程序的异常走这里
低级别32位模式      +0x600   +0x680   +0x700   +0x780
```

内核启动时把向量表安装好（[kernel.c](../../kernel/kernel/src/kernel.c)）：

```c
void _kernel_entry_c(void) {
    ...
    copy_interrupt_table();   // 把中断向量表放到指定内存
    ...
}
// AArch64 通过设置 VBAR_EL1 指向该表（在 arch 代码中完成）
```

## 4.4 异常处理的第一步：保存上下文

异常发生时用户的程序"正干到一半"——所有寄存器的值都是现场。
内核处理完异常还要让用户程序**从原处继续**，所以第一件事是
把全部寄存器压栈保存。看
[interrupt.S](../../kernel/platform/aarch64/arch/common/src/interrupt.S) 的宏：

```asm
.macro SAVE_IRQ_CONTEXT
    stp q30, q31, [sp, #-32]!   ; 保存 32 个 128 位浮点/向量寄存器
    ...                          ; （q0~q31，共 32 条）
    stp x28, x29, [sp, #-16]!   ; 保存 31 个 64 位通用寄存器
    ...                          ; （x0~x30）
    mrs x29, fpsr                ; 浮点状态寄存器
    mrs x28, fpcr
    stp x28, x29, [sp, #-16]!
    mrs x29, sp_el0              ; 用户态栈指针
    stp x29, x30, [sp, #-16]!
    mrs x29, spsr_el1            ; ★ 被打断时的特权级与状态
    mrs x28, elr_el1             ; ★ 被打断时的指令地址（返回点）
    stp x28, x29, [sp, #-16]!
.endm
```

两个最重要的寄存器：
- **ELR_EL1**：被打断时的指令地址。处理完 `eret` 跳回去，程序无缝继续；
- **SPSR_EL1**：被打断时的状态（当时在 EL0 还是 EL1、中断是否关闭）。

保存后栈上的内存布局正好就是内核的 `context_t` 结构，
调度器可以直接操作它——这是第 07 章上下文切换的基础。

处理完毕时执行对称的 `RESTORE_IRQ_CONTEXT`：恢复全部寄存器，
最后 `eret` 回到被中断的程序。

## 4.5 一次异常的完整生命周期

以"用户程序访问了未映射的内存"为例：

```
用户态(EL0) 程序执行 ldr x0, [x1]
        │ x1 指向非法地址
        ▼
CPU 硬件自动：
   1. ELR_EL1 ← 出错指令地址；  SPSR_EL1 ← EL0 状态
   2. 切到 EL1，跳到向量表"来自低级别的同步异常"入口(+0x400)
        ▼
向量表代码（interrupt.S）：
   SAVE_IRQ_CONTEXT          ← 保存现场到内核栈
   bl c_interrupt_handler    ← 进入 C 代码判断异常原因
        ▼
内核处理（缺页/非法访问/系统调用？）：
   - 系统调用：按编号服务（第 08 章）
   - 用户程序非法访问：杀死该进程
   - 缺页：分配物理页、更新页表（第 05 章）
        ▼
RESTORE_IRQ_CONTEXT + eret   ← 恢复现场，回到用户态继续执行
```

## 4.6 一次奇妙的时空穿梭：从内核态穿越到用户态

4.2 节我们演示了"降级"：从 EL2 到 EL1。现在要完成更关键的一次穿越——
**从内核态（EL1）出发，把一个用户进程"投放"到用户态（EL0）去**。
这是操作系统的"造人"仪式，第 07 章创建进程时会真正用到它。

先想清楚：CPU 正运行在内核态，怎么"变成"在用户态执行一段新代码？
答案是反过来用一次异常机制。`4.1` 说过，异常发生时硬件自动保存
`ELR`（返回地址）和 `SPSR`（返回后的状态）；`eret` 则按这两个寄存器复原。
那么——**如果内核主动把这两个寄存器填好，再执行 `eret`，
就等于凭空捏造了一次"异常返回"，CPU 就按内核指定的地点和级别"醒来"**。

### 穿越前，内核要布置好五件事

```
① 画好用户的世界：给新进程建页表（第 05 章的 clone 版），
   低半部映射它的代码、数据、栈——权限标记为"EL0 可访问"
② 装好它的世界：把新页表基址写入 TTBR0_EL1（低半部翻译词典换人）
③ 指定醒来的地点：ELR_EL1 ← 用户程序入口地址
④ 指定醒来的姿势：SPSR_EL1 ← EL0 状态编码（如 0x000，M[3:0]=0 表示 EL0t）
   SP_EL0 ← 用户栈顶
⑤ 清好口袋：通用寄存器清零（防止内核数据泄漏给用户）
```

然后一条指令点火：

```asm
eret          ; CPU 读取 SPSR/ELR，特权级降为 EL0，
              ; 从用户入口地址开始执行——穿越完成！
```

从这一刻起，那段代码就是一个"用户进程"：它碰不了硬件、改不了页表，
干任何危险的事都会触发异常被内核接住。**穿越是单程票**——
用户想回来，只有一条门：系统调用（第 08 章）。

### 穿越时到底发生了什么

把 `eret` 这一瞬间 CPU 内部的动作放慢看：

```
执行 eret 前的状态                      执行 eret 后的状态
─────────────────                      ─────────────────
特权级:  EL1（内核）          ───────►  特权级:  EL0（用户）
PC:     内核的 eret 指令      ───────►  PC:     ELR_EL1 里的用户入口
栈:     SP_EL1（内核栈）      ───────►  栈:     SP_EL0（用户栈）
页表:   低半部已是新进程的     ───────►  翻译生效：用户看到的都是自己的页
中断:   由 SPSR 的位决定      ───────►  按 SPSR 恢复
```

一次 `eret`，换了四样东西：**级别、代码、栈、内存视图**。
这就是"时空穿梭"的完整含义——进程从此活在自己的时空里，
直到下一次异常（中断/系统调用/出错）把它拉回内核。

### EwokOS 里它藏在哪

EwokOS 没有一条单独的"启动用户进程"指令，这个穿越被做进了
**上下文切换的统一通道**：内核为新进程准备一个 `context_t`
（寄存器现场，包括伪造好的 `elr`、`spsr`、栈指针），
`proc_switch` 恢复这个上下文后照常 `eret`——
对 CPU 来说，"第一次启动新进程"和"恢复一个被切走的旧进程"
用的是完全相同的代码路径。这个统一设计见第 07 章。

## 4.7 这一切与"操作系统"的关系

现在可以回答几个根本问题了：

1. **为什么用户程序不能读写硬件？**
   设备寄存器映射在内核页表里（第 05 章），EL0 访问触发同步异常，被内核拦截。
2. **用户程序怎么请求内核干活？**
   执行 `svc` 指令 → 触发同步异常 → 进入内核 → 内核按寄存器里的编号服务。
   这就是系统调用，第 08 章的主角。
3. **为什么程序崩溃不会拖垮系统？**
   一切异常都先经过内核的手。非法程序被杀掉，内核和其他进程继续运行。

## 4.8 动手练习

1. 打开 [boot.S](../../kernel/platform/aarch64/arch/v8/boot.S)，
   逐行读懂 `__entry` 到 `__el1_entry` 的降级过程；
2. 在 GDB 里给 `_kernel_entry_c` 打断点（第 02 章的 `make debug` + `make gdb`），
   启动后用 `p $ELR_EL1`（或 `info registers`）观察特权级相关寄存器；
3. 想一想：如果向量表本身被用户程序覆盖了会怎样？
   （答案：向量表内存只有内核可写——这就是第 05 章页表权限要解决的事。）

## 4.9 本章小结

- ARM 有 EL0~EL3 四个特权级：用户程序在 EL0，内核在 EL1；
- EwokOS 启动时通过"伪造异常返回"（`eret`）从 EL2 降到 EL1；
- 异常向量表是内核接住一切事件的总入口，16 个槽位按来源和类型分布；
- 处理异常的核心动作：保存现场（含 `ELR/SPSR`）→ C 代码处理 → 恢复现场 → `eret`；
- 反向用 `eret`（填好 `ELR/SPSR/TTBR0/SP_EL0`）即可完成内核态到用户态的穿越，
  这是创建用户进程的仪式；穿越是单程票，回来的门只有系统调用。
