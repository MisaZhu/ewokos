# 10 文件系统与存储设备

> 本章目标：理解数据如何从 SD 卡上的磁比特变成程序里的字节。
> 覆盖三层：SD 卡硬件驱动 → ext2 文件系统解析 → VFS 虚拟文件系统。
> 本章术语（VFS/inode/ext2/扇区/块/超级块/挂载…）见 [附录·术语表](99-术语表-专业名词速查.md)。

## 10.1 存储的三层抽象

```
┌────────────────────────────────────────────────┐
│ 应用看到的：  /etc/passwd 这样的路径与文件        │  ← VFS（vfsd 进程）
├────────────────────────────────────────────────┤
│ 文件系统：    inode、目录、块（4KB）              │  ← ext2/ext3（sdfsd 进程）
├────────────────────────────────────────────────┤
│ 块设备：      按 512 字节扇区读写的 SD 卡         │  ← SD 卡驱动
└────────────────────────────────────────────────┘
```

每一层只依赖下一层的接口。这样换文件系统、换存储介质都不影响其他层。

## 10.2 SD 卡是怎么读写的

SD 卡本质上是一串可以按扇区（512 字节）读写的存储器，
挂在树莓派的 SD 控制器上（Pi2/Pi3 是 SDHOST/EMMC 控制器）。
驱动依然是第 03 章的套路——写 MMIO 寄存器：

```
发命令（CMD17=读单块 / CMD18=读多块）
    → 等状态寄存器显示"完成"
    → 从数据寄存器把 512 字节搬出来
```

树莓派的实现在
[bsp/sd.c](../../machines/raspix/kernel/bsp/sd.c) 与
[bcm283x/src/sd.c](../../machines/raspix/kernel/lib/bcm283x/src/sd.c)（含初始化序列、
时钟协商等繁琐细节，初学可跳过内部，记住接口）：

```c
int32_t sd_read(uint32_t block, void* buf, uint32_t buf_size);
int32_t sd_write(uint32_t block, const void* buf, uint32_t buf_size);
```

> 微内核趣闻：启动早期内核需要亲自读 SD 卡（读配置、读 init），
> 所以内核里有一份 SD 驱动；系统跑起来后，用户态的 `sdfsd`
> 通过 `SYS_MEM_MAP` 把 SD 控制器寄存器映射进自己的内存，
> 再实现一份用户态驱动。两套代码服务不同阶段。

## 10.3 ext2：扇区之上如何组织文件

裸扇区只有编号（0, 1, 2, ...），"文件"概念需要数据结构来表达。
EwokOS 使用经典的 **ext2**（SD 镜像是 `mke2fs` 生成的）。
下面按"磁盘上真实长什么样"讲透。

### ① 整体布局：超级块 + 块组

```
SD 卡分区
├── 超级块 superblock        全局元信息：块大小、inode/块总数、魔数 0xEF53
├── 块组 0 (block group)
│   ├── 块位图               哪些数据块被占了（1=占 0=空）
│   ├── inode 位图           哪些 inode 被占了
│   ├── inode 表             一排 inode（档案），每个固定 128 字节
│   └── 数据块               真正的文件内容
├── 块组 1 ...               （结构重复，便于局部损坏时恢复）
```

对应 [ext2head.h](../../kernel/lib/ext2/include/ext2head.h) 的三个核心结构：

```c
typedef struct ext2_super_block {   // 超级块：整盘"说明书"
    uint32_t s_inodes_count;        // 共多少 inode
    uint32_t s_blocks_count;        // 共多少块
    uint32_t s_log_block_size;      // 块大小 = 1024 << 这个值
    uint16_t s_magic;               // 0xEF53，验明正身
    ...
} SUPER;

typedef struct ext2_inode {         // inode：单个文件的"档案"
    uint16_t i_mode;                // 类型+权限（目录/文件/可读写…）
    uint32_t i_size;                // 文件大小（字节）
    uint32_t i_block[15];           // ★数据块指针数组（见下）
    ...
} INODE;

typedef struct ext2_dir_entry_2 {   // 目录项："文件名 → inode 号"
    uint32_t inode;
    uint8_t  name_len;
    char     name[255];
} DIR;
```

### ② inode 如何指向数据：直接 + 间接

`i_block[15]` 不是都直接存数据块，而是分层：

```
i_block[0..11]  → 直接指向 12 个数据块（小文件到此为止）
i_block[12]     → 一级间接：指向一个"全是块号的块"（再多 ~1024 个块）
i_block[13]     → 二级间接（超大文件）
i_block[14]     → 三级间接（极少用到）
```

小文件一个 inode 就够了；大文件顺着间接指针一层层找。
**这就是"文件可以任意大、且物理上不必连续"的秘密**。

### ③ 目录 = 特殊的文件

目录的"内容"就是一串目录项。读 `/etc/passwd` 其实是三步链式查找：

```
读 "/" 目录（根 = inode 2）→ 扫目录项，找到 "etc" 对应的 inode 号
读 /etc 目录               → 扫目录项，找到 "passwd" 对应的 inode 号
读该 inode                → 按 i_block 指针列表把数据块逐块读出
```

### ④ 内核里的读文件算法

内核自带一份**只读**的 ext2 实现（[kernel/lib/ext2/](../../kernel/lib/ext2/)），
启动时用来读配置和 `/sbin/init`。看
[ext2read.c](../../kernel/lib/ext2/src/ext2read.c) 的关键函数链：

```
sd_read_ext2(fname, &size)          ← 入口：给路径，要内容
  └─ ext2_init：读超级块、验证魔数、算出块组数、载入所有块组描述符
  └─ ext2_readfile
      └─ ext2_ino_by_fname          ← 把路径变成 inode 号
          └─ split_fname("/etc/passwd") → ["etc","passwd"]
          └─ 逐级 search()：读当前目录，线性扫描目录项匹配文件名
      └─ get_node_by_ino            ← 按 inode 号定位并读出 INODE
      └─ ext2_read(node, buf, n, off) ← 按 i_block 逐块读进 buf
```

底层读块靠 `read_block` 函数指针——内核启动阶段它就是
"调 SD 驱动读 512 字节扇区"。看 [loadinit.c](../../kernel/loadinit/sd/loadinit.c)：

```c
int32_t load_init_proc(void) {
    const char* prog = "/sbin/init";
    char* elf = read_fs(prog, &sz);        // ★在 SD 卡的 ext2 里找文件
    if(elf != NULL) {
        proc_t *proc = proc_create(TASK_TYPE_PROC, NULL);
        proc->info.uid = -1;               // uid=-1 是"内核亲自加载"的标记
        proc_load_elf(proc, elf, sz);      // 解析 ELF 建立进程（第 07 章）
        ...
    }
}
```

**这是内核最后一次亲自碰文件系统**——之后一切文件操作都交给用户态了。

## 10.4 VFS：一切皆文件的统一入口

用户态的文件系统架构：

```
         ┌──────────────┐
应用 ──► │    vfsd       │ 挂载表：  /      → sdfsd (SD卡 ext2)
         │  （路由器）    │          /tmp   → ramfsd (内存盘)
         └──┬───────┬───┘          /dev/* → 各设备驱动进程
            │       │
        ┌───▼──┐ ┌──▼───┐
        │ sdfsd │ │ramfsd│ ...   每个挂载点是一个独立的 IPC 服务
        └──────┘ └──────┘
```

- **`vfsd`**（[vfsd.c](../../system/basic/sys/vfsd/vfsd.c)）：维护挂载表，
  解析路径，把请求转发给对应挂载点的服务。它自己**不实现任何文件系统**；
- **`sdfsd`**：ext2/ext3 的完整实现（读写）；
- **`ramfsd`**：内存文件系统（`/tmp`）；
- **设备即文件**：`/dev/tty0`（串口）、`/dev/timer`、`/dev/log`……
  每个都是一个驱动进程提供的虚拟文件。`printf` 最终变成对某个
  `/dev/*` 的写操作——这就是 Unix "一切皆文件" 哲学的微内核版。

### 挂载表长什么样

`vfsd` 里的挂载表就是一个数组，每行是一个 `mount_t`
（[fsinfo.h](../../system/basic/libc/libewoksys/ewoksys/include/ewoksys/fsinfo.h)）：

```c
typedef struct {
    int32_t pid;                  // 这个挂载点由哪个服务进程提供
    ewokos_addr_t org_node;       // 该文件系统里的"根节点"句柄
    char org_name[FS_FULL_NAME_MAX];  // 挂载路径，如 "/"、"/tmp"
} mount_t;
```

收到路径 `/tmp/a.txt` 时，`vfsd` 找**最长的匹配前缀** `/tmp`，
把请求转给 `ramfsd`（它的 `pid`），并把 `/a.txt` 作为"相对该挂载点"的
路径传过去。路径里每个节点还有一个 `fsinfo` 结构记录
类型（目录/文件/字符设备/块设备）、归属的挂载服务、状态等。

### 文件操作 = 一组固定的命令号

所有文件操作都收敛成一组枚举 `FS_CMD_*`，走第 09 章的 IPC：

```c
enum {
    FS_CMD_NONE = 0,
    FS_CMD_OPEN,        // 打开
    FS_CMD_STAT,        // 查属性
    FS_CMD_CREATE,      // 新建
    FS_CMD_CLOSE,       // 关闭
    FS_CMD_READ,        // 读
    FS_CMD_WRITE,       // 写
    FS_CMD_SEEK,        // 移动读写位置
    FS_CMD_UNLINK,      // 删除
    FS_CMD_FLUSH,       // 刷缓冲
    ...
};
```

于是 `read(fd, buf, n)` 在底层就是：

```
libc → ipc_call(挂载点服务的pid, FS_CMD_READ, 打包{fd, n})
     → 服务进程读数据 → 把字节塞进 proto_t 返回
     → libc 解包到 buf
```

**文件系统的"API"被压成了一张命令号表**，任何语言、任何进程
都能靠发 IPC 用上它。设备文件同理——`FS_CMD_DEV_CNTL` 还能
给驱动发"厂商自定义命令"（比如弹出 U 盘）。

## 10.5 跟着做：观察文件系统

启动系统后：

```
> ls /                  # 看根目录
> cat /etc/passwd       # 读文件：走 vfsd → sdfsd → SD 卡
> echo hi > /tmp/a.txt  # 写文件：走 vfsd → ramfsd → 内存
> cat /tmp/a.txt
> df                    # 查看挂载表
```

每个命令背后都是多次 IPC 调用。可以用 `svcinfo` 看服务进程列表，
把命令和挂载表对上。

   有没有更省的办法？（提示：`nulld` 极简，
   但微内核宁可多一个进程也要保持"设备=独立服务"的一致性。）

## 10.7 本章小结

- 存储三层：块设备（扇区）→ 文件系统（inode/目录）→ VFS（路径）；
- SD 卡驱动就是按手册操作控制器寄存器；
- ext2 用 inode + 目录组织文件；内核只在启动阶段读它（加载配置和 init）；
- 运行期文件操作全部是应用 → `vfsd` → 具体文件系统进程的 IPC 链；
- 设备也是文件，每个 `/dev/*` 背后是一个驱动进程。
