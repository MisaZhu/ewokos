# 09 IPC 进程间通信

> 本章目标：理解微内核的血液——IPC。看懂一次 `open("/a.txt")`
> 背后客户端、内核、服务端三方的完整协作。这是理解 EwokOS 一切
> 上层设施（文件系统、窗口系统、网络）的钥匙。
> 本章对应实验主线的"第 7 套代码"：微内核操作系统的精华。
> 更深入的细节仓库里有专门文档：[docs/ipc.md](../ipc.md)。
> 本章术语（IPC/RPC/proto_t/ipc_task_t/shm/DMA…）见 [附录·术语表](99-术语表-专业名词速查.md)。

## 9.1 微内核为什么必须解决通信问题

第 01 章说过：文件系统、驱动、窗口系统都是独立的用户态进程。
它们之间必须互相调用，比如：

- `shell` 要调用 `vfsd` 读文件；
- `vfsd` 要调用 `sdfsd` 读 SD 卡；
- 窗口程序要调用 `xserverd` 画图。

### 进程间通信的实现方法有哪些

进程被页表隔离在不同内存世界里（第 05 章），想交换数据，经典路子有这些：

| 方法 | 原理 | 特点 |
|---|---|---|
| 共享内存 | 双方页表映射同一块物理页，直接读写 | 最快（零拷贝），但要自己解决同步 |
| 管道/消息队列 | 内核维护一块缓冲，一方写一方读 | 简单，但"何时该来取货"需要额外通知 |
| 信号 | 一发一收的简短通知 | 只能传几十字节的"事件"，不能传数据 |
| 消息传递（RPC，Remote Procedure Call，远程过程调用） | 一方发请求阻塞等，另一方处理完回复 | 天然同步、天然带服务语义 |

注意一个事实：**这些方法全都绕不开内核**——只有内核能同时看到两个
进程的页表，也只有内核能唤醒/阻塞进程。所以"进程间通信"本质上是
**借内核之手传递**，区别只在传什么、怎么传。

EwokOS 的选择：**消息传递 + 同步语义的远程过程调用（RPC）**。
它不额外提供端口、管道、消息队列这些设施——内核自己**就是**消息中介。

```
┌─────────────────────┐                        ┌──────────────────────────────┐
│ 客户端进程           │                        │ 服务端进程                    │
│                     │  SYS_IPC_CALL          │                              │
│ ipc_call(pid, cmd,  │ ─────────────────────► │ ipc 入口函数                 │
│        in, out)     │     内核分配 ipc 任务    │   ipc_get_arg(uid)           │
│                     │                        │   ... 处理 cmd ...           │
│ 阻塞，等待回复        │                        │   ipc_set_return(uid, out)   │
│                     │ ◄───────────────────── │   ipc_end()                  │
│ ipc_get_return()    │  内核唤醒客户端           │                              │
└─────────────────────┘                        └──────────────────────────────┘
```

一次调用 = 客户端阻塞 + 服务端执行 + 客户端被唤醒。简单、可预测，
像本地函数调用一样用。

## 9.2 服务端：如何成为一个服务

任何进程调用 `ipc_serv_run()` 主循环就能变成服务器
（[ipc_serv.c](../../system/basic/libc/libewoksys/ewoksys/src/ipc_serv.c)）。
框架大致是：

```c
// 伪代码：一个服务进程的主循环
void ipc_serv_run(ipc_serv_t* serv, void(*handler)(ipc_serv_t*, int32_t uid)) {
    while(1) {
        uid = ipc_serv_wait();       // 睡眠，直到有请求到来
        handler(serv, uid);          // 处理请求
        ipc_end(uid);                // 通知内核：这个请求结束了
    }
}
```

**请求是怎么"到来"的？** 回忆第 07 章的上下文劫持：
客户端发起调用后，内核把服务端进程标记为待处理，
服务端下次被调度时直接从注册的 **ipc 入口函数** 开始执行，
参数（任务号 `uid`）通过寄存器传入。处理完 `ipc_end()`，
内核恢复它原来的上下文，继续主循环——它根本感知不到切换发生过。

### 单任务模式与多任务模式

- **单任务模式（默认）**：整个进程同时只处理一个请求，
  处理期间其他客户端的请求排队（内核让调用方进入等待，
  返回 `IPC_ERROR_RETRY` 语义）。简单，但慢请求会阻塞所有人；
- **多任务模式（`IPC_MULTI_TASK`）**：内核为服务维护一个
  **工作线程池**，多个请求被分配到不同线程并行处理。
  文件系统、窗口服务器这类高并发服务用它。

## 9.3 客户端：如何调用一个服务

客户端用库函数 `ipc_call`（[ipc.c](../../system/basic/libc/libewoksys/ewoksys/src/ipc.c)）：

```c
proto_t in, out;
proto_init(&in, buf_in, sizeof(buf_in));
proto_init(&out, buf_out, sizeof(buf_out));

proto_add_int(&in, 参数1);              // 打包参数
int res = ipc_call(服务进程pid, 命令号, &in, &out);  // ★同步等待结果
if(res == 0) {
    int value = proto_read_int(&out);   // 解包结果
}
```

数据打包用 `proto_t`（[proto.c](../../system/basic/libc/libewoksys/ewoksys/src/proto.c)）：
一个带长度前缀的字节包，支持整数、字符串、二进制块。
为什么不用结构体直接传？因为两个进程的内存空间互相不可见，
必须先把数据**拷贝到内核中转区**再复制到对方空间——
打包成字节流最简单可靠。

### 进程间数据交换的效率

诚实面对代价：一次普通 `ipc_call` 的数据要经历
**用户 → 内核 → 用户**的至少两次拷贝，外加两次上下文切换。
对"打开文件"这类小请求，开销可以忽略；
但对"把 800×480 位图发给显示驱动"这种大数据，拷贝就是灾难。

EwokOS 的答案是**分级**：

| 数据规模 | 手段 | 拷贝次数 |
|---|---|---|
| 几十字节的参数 | `proto_t` 消息 | 2 次，无所谓 |
| 大块数据（图像/缓冲） | **共享内存**（`SYS_PROC_SHM_*`）：
  双方页表映射同一块物理页，IPC 只传一个"句柄" | 0 次 |
| 需要内核/设备直达的缓冲 | 连续物理内存映射（DMA 场景） | 0 次 |

记住微内核的效率法则：**控制信令走消息，大块数据走共享内存**。
第 13 章的图形系统（xwin）正是把这两条用到极致——
窗口画面全部放在共享内存里，IPC 只传"哪块画布脏了"这样的短消息。

## 9.4 内核侧：IPC 的真实数据结构

现在深入到 [ipc.c](../../kernel/kernel/src/ipc.c) 的内脏。
微内核的精华不在"消息"这个概念，而在**内核为每个服务进程维护的一套状态机**。
看懂下面三个结构体，你就真正读懂了 EwokOS 的 IPC。

### ① 一次请求 = 一个任务槽（ipc_task_t）

客户端每发起一次调用，内核就在服务端占一个**任务槽**：

```c
typedef struct {
    uint32_t  uid;          // 本次调用的全局编号（内核递增分配）
    uint32_t  counter;
    uint32_t  state;        // IPC_BUSY：正在被处理
    proto_t   arg_ret;      // ★参数与返回值共用的一块缓冲
    int32_t   client_pid;   // 是谁调用的我
    uint32_t  client_uuid;  // 防 pid 复用的二次校验
    uint8_t   client_intr;  // 调用方是否在中断上下文里
    int32_t   call_id;      // 命令号（含 IPC_LAZY 等标志位）
    int32_t   handler_pid;  // 多任务模式：哪个工作线程在伺候我
    uint32_t  handler_uuid;
} ipc_task_t;
```

关键点：`arg_ret` 这块缓冲**先装客户端传来的参数，处理完后被结果覆盖**。
也就是说"参数"和"返回值"复用同一块内存，靠 `state` 区分阶段。

### ② 一个服务的总账本（ipc_server_t）

每个注册为服务的进程，其 `space` 里都嵌着一个 `ipc_server_t`：

```c
typedef struct {
    int32_t       lock;          // SMP 自旋锁（多核同时调用时用）
    bool          disabled;      // 暂停接客（升级/维护时暂时不收新请求）
    bool          multi_task;    // 单任务？多线程池？
    ewokos_addr_t entry;         // ★ipc 入口函数的地址（上下文劫持的跳板）
    ipc_task_t    tasks[IPC_CTX_MAX];  // 任务槽数组，IPC_CTX_MAX = 8
    uint8_t       task_head, task_tail, task_num;   // 环形队列头尾
    ipc_pool_worker_t* pool;     // 多任务模式的工作线程池
    bool          do_switch;     // 单任务模式：内核已劫持上下文，待切换
    ewokos_addr_t stack;         // 劫持时用的独立内核栈
    saved_state_t saved_state;   // ★被劫持前的原始上下文快照
    ipc_queue_item_t* wait_head, wait_tail;  // 服务端忙时，客户端排队
} ipc_server_t;
```

三件事值得记牢：

1. **任务槽是定长数组**（8 个），不是动态分配——避免服务忙时内核还得
   `kmalloc`；满了就让后来的客户端排队；
2. **`entry` 是劫持跳板**：客户端调用后，内核让服务进程从 `entry`
   地址开始执行，而不是继续它原来的 `main` 循环；
3. **`saved_state` 是还原点**：劫持前把服务原来的寄存器现场存这里，
   `ipc_end()` 时再还原回去——这就是第 07 章"上下文劫持"的具体实现。

### ③ 参数怎么跨进程：proto_t 字节包

两个进程的内存互相不可见，参数必须**拷贝过内核**。`proto_t`
（[proto.c](../../system/basic/libc/libewoksys/ewoksys/src/proto.c)）
就是一段"自描述字节流"：

```c
typedef struct {
    void*    data;        // 数据缓冲（小数据用内置 buffer，大数据才 malloc）
    uint32_t size;        // 当前已写入字节数
    uint32_t total_size;
    uint32_t offset;      // 读到哪了
} proto_t;
```

- 写入：`proto_add_int(&p, x)` 把整数按定长追加到 `data` 尾部；
- 读取：`proto_read_int(&p)` 从 `offset` 处顺序取出并推进偏移；
- **跨进程时**内核用 `proto_copy` 把整段 `data` 复制到对方空间。

为什么不用结构体直接传？因为结构体里的指针在对方地址空间里是无效的，
必须摊平成"纯数据"的字节流。打包成字节流最简单、最可靠、也最可移植。

## 9.5 内核侧：一次调用的完整旅程

现在把数据结构串成流程。`SYS_IPC_CALL` 进入内核的
`proc_ipc_call`（[ipc.c](../../kernel/kernel/src/ipc.c)），分两种模式走。

### 单任务模式（默认，多数驱动）

```
A: SYS_IPC_CALL(B, cmd, arg)
   ├─ 内核 proc_ipc_req：在 B 的任务槽环形队列尾部占一个槽，
   │   proto_copy 把 A 的参数复制进槽；槽满则把 A 挂到 wait 队列
   ├─ 内核 proc_ipc_do_task：
   │   ① 把 B 当前上下文存进 B->saved_state（存还原点）
   │   ② 置 B->do_switch = true
   │   ③ proc_switch 直接把 CPU 切给 B
   └─ A 阻塞等回复
B: 被调度 → 从 entry（ipc 入口）开始执行，寄存器里是任务号 uid
   ├─ 处理请求…
   ├─ SYS_IPC_SET_RETURN：把结果写进任务槽的 arg_ret
   └─ SYS_IPC_END → proc_ipc_end：
       ① 从 saved_state 还原 B 原来的上下文（B 回到自己的 main 循环）
       ② 关闭任务槽、把结果复制给 A、唤醒 A
       ③ 若队列里还有请求，直接继续处理下一个
A: 从阻塞处醒来，ipc_get_return 拿到结果
```

**注意单任务模式的代价**：B 的整个进程一次只伺候一个请求，
慢请求会阻塞后面所有人。驱动这类"快进快出"的服务用它正好。

### 多任务模式（`IPC_MULTI_TASK`，xserverd/文件系统）

高并发服务不能串行等待。内核给它维护一个**工作线程池**：

```
A: SYS_IPC_CALL(B, cmd, arg)
   ├─ proc_ipc_req：在 B 的任务槽里随便找一个空槽（不要求顺序）
   ├─ ipc_pool_assign：找一个绑在 A 所在核上的空闲工作线程；
   │   没有就按需孵化一个新线程（上限 = 进程线程数限制）
   └─ proc_switch 直接把 CPU 交给那个工作线程 → 请求立刻开跑
B 的工作线程: 执行 entry → 处理 → ipc_end → 线程"泊车"待复用
   └─ 空闲 3 秒还没活，线程自动退出，归还线程槽
A: 被唤醒拿到结果
```

两个变体要分清：

- **`IPC_MULTI_TASK`**：可孵化多个工作线程并行处理，客户端排队等线程；
- **`IPC_MULTI_CORE`**：每个 CPU 核**最多一个**工作线程，核忙了立刻
  返回 `IPC_ERROR_RETRY` 让调用方重试——更省线程、更适合"每核独立"的场景。

线程池的设计哲学（源码注释里写得很清楚）：**池从空开始，按需孵化，
用完泊车复用，闲了自动缩回空**。既不浪费内存，也不预热无关线程。

### 错误码

[syscalls.h](../../kernel/kernel/include/syscalls.h) 定义三个哨兵值，
都通过 `ctx->gpr[0]` 传回用户态：

```c
#define IPC_ERROR_RETRY      -1   // 服务端忙/禁用，内核阻塞调用方稍后重试
#define IPC_ERROR_SELF       -2   // 不能调用自己（会死锁）
#define IPC_ERROR_NO_READY   -3   // 对方还没注册 ipc 服务
```

`IPC_ERROR_RETRY` 不是"失败"，而是"等一下再来"——
libc 会在被唤醒后自动重发这次调用。这是微内核里最常见的流控协议。

## 9.6 如何找到服务：名字服务（core）

调用需要对方进程的 pid，但"文件系统服务的 pid 是多少？"
每次开机可能不同。EwokOS 用 `core` 进程做**名字服务**：

```
服务启动时：  ipc_serv_reg("vfs", 服务id)  → core 记下 "vfs → pid 3"
客户端调用：  get_serv_pid("vfs")          → 向 core 查询 → 拿到 pid 3
```

`core` 还负责系统级协调（如当前目录、主机名），所以它必须是
**第二个启动的进程**——这正是第 11 章 `init` 先启动 `/sbin/core` 的原因。

## 9.7 用 IPC 的视角重看"读文件"

现在你能完整解释第 01 章那张图了：

```
应用: open("/etc/passwd")
  → libc: ipc_call(vfsd_pid, VFS_CMD_OPEN, ...)      【IPC 第 1 跳】
  → vfsd: 查挂载表，发现 "/" 由 sdfsd 提供
  → vfsd: ipc_call(sdfsd_pid, FS_CMD_OPEN, ...)      【IPC 第 2 跳】
  → sdfsd: 通过 SYS_MEM_MAP 访问 SD 卡控制器读扇区，
           解析 ext2 目录，找到 inode
  → 结果原路返回，应用拿到一个文件句柄
```

**内核全程只搬运消息。** 文件系统代码哪怕全是 bug，崩溃的也只是 `sdfsd` 一个进程。

## 9.8 微内核，通信即服务

学到这里，可以提炼出微内核的世界观了：

> **在微内核里，"服务"不是内核里的一段代码，而是"一个可以被调用的进程"。
> 想用什么能力，就给那个进程发一次消息。通信即服务。**

推论一：**一切上层设施都是同一个模式**。文件系统是 `vfsd` 这个进程，
窗口系统是 `xserverd` 这个进程，网络是 `netd` 这个进程——
它们的"API"统统是一次 `ipc_call`。学会第 09 章，等于同时学会了
第 10、13 章和（下册的）网络章的骨架。

推论二：**服务可以崩溃、可以重启、甚至可以升级**。
客户端调用时服务端挂了，内核只会返回一个错误码，客户端自己决定重试还是放弃；
系统不跟着陪葬。这是宏内核做不到的弹性。

推论三：**服务也可以被替换**。只要协议（命令号与参数格式）不变，
`vfsd` 的实现可以整个换掉，其他进程毫无察觉。
这就是"面向消息的架构"带来的解耦。

回头看整个教程：第 03~08 章造出的进程、特权级、系统调用、调度，
都是为了支撑这一章的一句话——**让互相隔离的进程能安全地互相服务**。
这就是微内核操作系统的精华。

## 9.9 动手练习

1. 启动系统后运行 `svcinfo`（或 `ps` 对照启动日志），
   找出系统中所有的服务进程（`uartd`、`vfsd`、`timerd`…）；
2. 在 [core.c](../../system/basic/sys/core/core.c) 中找到服务注册表，
   看看 `vfs`、`sd` 这些名字如何映射到 pid；
3. 思考题：客户端调用服务端时如果服务端进程崩溃了，会发生什么？
   （提示：内核会唤醒等待的客户端并返回错误——在 `ipc.c` 里找找这段逻辑。）

## 9.10 本章小结

- IPC 的实现方法有共享内存/管道/信号/消息传递，全都借内核之手完成；
- EwokOS IPC 是同步 RPC：客户端阻塞、内核中转、服务端执行、结果唤醒；
- 内核为每个服务维护 `ipc_server_t`：定长 8 个任务槽、劫持跳板 `entry`、
  还原点 `saved_state`、忙时等待队列；一次请求就是一个 `ipc_task_t` 槽；
- 单任务模式靠"上下文劫持"串行处理，`IPC_MULTI_TASK`/`IPC_MULTI_CORE`
  用按需孵化、泊车复用的工作线程池并行；
- 参数用 `proto_t` 自描述字节流中转；效率法则：小数据走消息，大数据走共享内存；
- `core` 进程提供名字服务，让服务发现与 pid 解耦；
- 微内核的世界观：通信即服务——文件系统、窗口、网络全建立在它之上。
