# 08 系统调用

> 本章目标：理解用户程序如何安全地请求内核服务。跟着一行 `getpid()`
> 走完"用户态 → 内核 → 用户态"的完整旅程，看懂系统调用表与分发器。

## 8.1 大门只开一条缝

回顾第 04 章：用户程序（EL0）不能碰硬件、不能改页表、不能碰内核内存。
但程序总要干活——读文件、申请内存、创建进程。怎么办？

内核开了一条**受控的门缝**：`svc`（Supervisor Call）指令。
任何程序都可以执行它，但执行后控制权交给内核，由内核决定干什么。

```
用户程序:  "我想打印字符串"
    │
    │ 执行  svc #0          （唯一的钥匙）
    ▼
CPU:  触发同步异常 → 进入内核（EL1）→ 跳到向量表对应入口
    ▼
内核:  检查请求编号与参数 → 执行服务 → 把结果写回
    ▼
用户程序:  拿到返回值继续跑
```

## 8.2 用户侧：一次系统调用的发起

EwokOS 的用户态 C 库把所有系统调用统一成 4 个宏
（[syscall.h](../../system/basic/libc/libewoksys/ewoksys/include/ewoksys/syscall.h)）：

```c
// 最多 3 个参数的统一入口
extern ewokos_addr_t syscall3_raw(int code, arg0, arg1, arg2);

#define syscall3(code, arg0, arg1, arg2) syscall3_raw(code, arg0, arg1, arg2)
#define syscall2(code, arg0, arg1)       syscall3_raw(code, arg0, arg1, 0)
#define syscall1(code, arg0)             syscall3_raw(code, arg0, 0, 0)
#define syscall0(code)                   syscall3_raw(code, 0, 0, 0)
```

底层实现短到极致（[syscall_aarch64.S](../../system/basic/libc/libewoksys/ewoksys/src/syscall_aarch64.S)）：

```asm
.global syscall3_raw
syscall3_raw:
    svc #0        ; 就这一条！按 ARM 调用约定：
    ret           ; x0=编号  x1=参数1  x2=参数2  x3=参数3
                  ; 返回值从 x0 带回
```

参数通过寄存器传递：`x0` 放系统调用编号，`x1~x3` 放参数，结果从 `x0` 返回。
比从内存传参快得多，也不需要共享内存结构。

## 8.3 系统调用号：一张总表

所有编号定义在 [syscalls.h](../../kernel/kernel/include/syscalls.h)，
是一个简单的枚举（节选）：

```c
enum {
    SYS_NONE = 0,
    SYS_KPRINT,          // 内核控制台打印
    // 进程内存管理
    SYS_MALLOC_EXPAND,   // 扩展堆
    SYS_FREE,
    // 进程生命周期
    SYS_EXEC_ELF,        // 加载 ELF 可执行文件
    SYS_FORK,            // 创建子进程
    SYS_THREAD,          // 创建线程
    SYS_YIELD,           // 主动让出 CPU
    SYS_WAIT_PID,        // 等待子进程结束
    SYS_USLEEP,          // 睡眠
    SYS_EXIT,            // 退出
    SYS_SIGNAL_SETUP,    // 信号
    SYS_GET_PID,
    // IPC（第 09 章）
    SYS_IPC_SETUP, SYS_IPC_CALL, SYS_IPC_END, ...
    // 共享内存 / 信号量 / DMA ...
    SYS_CALL_NUM         // 总数（约 60 个）
};
```

注意数量：**只有约 60 个**。对比 Linux 的 300+，这就是微内核的体现——
文件系统、网络、设备控制统统不在内核，走 IPC（第 09 章）。
内核只保留"必须用特权才能做"的事。

## 8.4 内核侧：分发器

`svc` 异常进入内核后，汇编保存好上下文，最终调用
[内核的分发器](../../kernel/kernel/src/svc.c)（简化）：

```c
static inline void _svc_handler(int32_t code, ewokos_addr_t arg0,
                                ewokos_addr_t arg1, ewokos_addr_t arg2,
                                context_t* ctx) {
    switch(code) {
    case SYS_EXIT:
        sys_exit(ctx, arg0);
        return;
    case SYS_KPRINT:
        sys_kprint((const char*)arg0, arg1);   // 打印用户给的字符串
        return;
    case SYS_GET_PID:
        ctx->gpr[0] = sys_getpid(...);          // 结果写进 x0 → 返回给用户
        return;
    case SYS_IPC_CALL:
        ...                                     // IPC（第 09 章）
    ...
    }
}
```

三个要点：

1. **返回值约定**：把结果写进 `ctx->gpr[0]`（即恢复现场时的 `x0` 寄存器）。
   成功返回 0 或正数（如新的 pid），失败返回负数（如 `-1`）；
2. **安全性**：用户传来的指针参数，内核访问前必须确认它确实位于
   该进程的地址空间，否则一个恶意程序就能让内核读写任意内存；
3. **SMP 保护**：分发前后用 `kernel_lock()` 串行化
   （只读查询类系统调用走快路径，不拿锁，见 `svc_is_query_fastpath`）。

## 8.5 完整旅程：`getpid()` 的一生

现在把整条链路串起来：

```
① 应用代码：     pid = getpid();
② C 库(libc)：   syscall0(SYS_GET_PID)
③ 汇编：         x0 = SYS_GET_PID; svc #0
④ CPU 硬件：     切到 EL1，跳向量表同步异常入口
⑤ interrupt.S：  SAVE_IRQ_CONTEXT（保存全部寄存器）
⑥ svc.c：        _svc_handler(code=SYS_GET_PID, ctx)
                 ctx->gpr[0] = 当前进程 pid
⑦ interrupt.S：  RESTORE_IRQ_CONTEXT + eret
⑧ 应用代码：     从 x0 拿到 pid，继续执行
```

一次系统调用的开销 = 一次异常的进出。这就是为什么微内核要控制调用次数
（能合并的合并，能用共享内存的不用拷贝——第 13 章图形系统会体现）。

## 8.6 错误处理约定

- 系统调用失败统一返回负数：`-1` 表示一般失败，
  特殊场景有专用值（如 `IPC_ERROR_RETRY = -1` 要求调用方重试）；
- C 库层把负数翻译成标准 `errno`（[errno.h](../../system/basic/libc/libgloss/errno.h)），
  用户程序按 POSIX 习惯检查：

```c
int fd = open("/a.txt", O_RDONLY);
if(fd < 0) {
    // errno 已被库函数设置
    slog("open failed: %d\n", errno);
}
```

## 8.7 动手练习

1. 用 GDB 跟踪一次系统调用：在 `svc.c` 的 `_svc_handler` 打断点，
   系统启动后任意进程执行系统调用都会停下，`p code` 看编号，
   对照 `syscalls.h` 查出它是什么；
2. 数一数启动日志中 `init: /sbin/core [ok]` 背后发生了多少次系统调用
   （提示：`fork`、`SYS_EXEC_ELF`、`SYS_IPC_*`……）；
3. 思考题：为什么 `SYS_KPRINT` 允许任何进程调用，但 `SYS_MEM_MAP`
   （映射设备内存）只应给受信任的驱动进程？内核该如何区分？
   （提示：看 `svc.c` 中对 `proc->info.uid` 的检查。）

## 8.8 本章小结

- `svc #0` 是用户进入内核的唯一大门，编号和参数走寄存器；
- 系统调用表只有约 60 项——微内核把其他服务都推给了 IPC；
- 分发器 `_svc_handler` 按编号 switch，结果写入 `ctx->gpr[0]`；
- 失败返回负数，C 库翻译成 `errno`。
