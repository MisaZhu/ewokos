# 07 进程与调度器

> 本章目标：理解"进程"在内核里就是一个结构体，看懂上下文切换
> 与调度算法的完整实现，理解 fork / exec / exit 的生命周期。
> 本章承载实验主线的三个里程碑："第 4 套代码"（第一个用户态进程）、
> "第 6 套代码"（进程调度）、"第 8 套代码"（fork）。
> 本章术语（pid/ELF/fork/exec/ZOMBIE/SMP/上下文…）见 [附录·术语表](99-术语表-专业名词速查.md)。

## 7.1 什么是进程

程序（Program）是躺在磁盘上的死代码；**进程（Process）**是运行中的代码：
它有当前的执行位置（程序计数器）、数据（寄存器、栈、堆）、自己的内存空间。

打个比方：程序是菜谱，进程是正在做菜的那次烹饪——
同样的菜谱可以同时进行多份（同一个程序跑多个进程），
每一份都有自己的进度、食材和灶台。

所以内核描述一个进程，只需要三样东西：

```c
// kernel/kernel/include/kernel/proc.h（简化）
typedef struct st_proc {
    proc_info_t   info;      // 身份与状态：pid、父进程、uid、状态、所在核心...
    proc_space_t* space;     // 内存空间：页表、堆、共享内存表、IPC 服务端...
    context_t     ctx;       // 上下文：全部寄存器的快照（CPU 现场的存档）
    ...
} proc_t;
```

其中 `context_t` 就是第 04 章异常处理时压栈保存的那份寄存器快照——
**进程被暂停 = 把寄存器存进 `ctx`；进程恢复 = 把 `ctx` 装回寄存器**。
上下文切换的全部魔法仅此而已。

这就是**进程的三要素**，缺一不可：

| 要素 | 回答的问题 | 没有它会怎样 |
|---|---|---|
| `info`（身份与状态） | 它是谁？现在什么状态？ | 内核无从管理 |
| `space`（内存空间） | 它住在哪里？ | 无法隔离，互相踩踏 |
| `ctx`（寄存器现场） | 它干到哪了？ | 无法暂停和恢复 |

进程在内核里存放在一张固定大小的**进程表**里（大小由配置
`max_proc_num` 决定），启动时由 `procs_init()` 初始化。

## 7.2 操作系统的第一个孩子：进程是如何创建的

理论都在了，现在看一次真实的"造人"。内核启动的最后一步
（[kernel.c](../../kernel/kernel/src/kernel.c)）：

```c
load_init_proc();   // 创建第一个用户进程 /sbin/init
```

这一步浓缩了创建一个进程的**全部工序**，共六步：

```
① 在进程表里找一个空槽位，分配 pid，状态置为 READY
② 造内存空间：clone 一份页表（第 05 章 5.8），高半部共享内核，低半部留空
③ 装内容：把 /sbin/init 的程序镜像读进来（启动期靠内核内置的精简
   ext2 驱动直接读 SD 卡，第 10 章详述），映射进低半部
④ 配上下文：ctx 的 pc ← 程序入口，sp ← 栈顶，
   spsr ← EL0（第 04 章 4.6 的"穿越五件套"）
⑤ 放进就绪队列
⑥ 等调度器选中它，proc_switch 恢复 ctx + eret —— 孩子出生，活在用户态
```

注意第 ③ 步的鸡生蛋：此时文件系统还没启动，`/sbin/init` 是**内核自己
从 SD 卡上读出来**的。这就是为什么内核里保留了一小段精简的
ext2 读代码（[kernel/lib/ext2](../../kernel/lib/ext2)）——
仅仅为了把第一个孩子生下来。孩子出生后（init 启动 `vfsd`/`sdfsd`），
这段代码就功成身退，之后再也没人用它加载程序。

从这里开始，系统里每一个新进程都由**已有进程**通过 `fork`/`exec` 诞生，
沿着父子链一路追溯到 init——进程世界和生命世界一样，有自己的谱系。

## 7.3 进程状态机

每个进程有一个状态（[procinfo.h](../../kernel/kernel/include/procinfo.h)）：

```
              fork/唤醒
                 │
                 ▼
   ┌──────► READY（就绪：排队等 CPU）
   │            │ 被调度器选中
   │            ▼
   │        RUNNING（运行中）
   │            │
   │            ├── 时间片到 ───────────┐
   │            ├── 等待事件(等待/睡眠)  │
   │            │        ▼              │
   │            │      WAIT（阻塞）─────┘ 事件到达，唤醒
   │            ├── 正常结束
   │            │        ▼
   │            └──► ZOMBIE（僵尸：等父进程收尸）
   │                         │ 父进程 wait
   └─────────────────────────┴──► UNUSED（释放）
```

## 7.4 就绪队列与调度器

每个 CPU 核心有一条**就绪队列** `_ready_queue[core]`，
状态为 READY 的进程排在里面。调度器代码出乎意料地短
（[schedule.c](../../kernel/kernel/src/schedule.c)）：

```c
int32_t schedule(context_t* ctx) {
    uint32_t core = get_core_id();
    proc_t* idle_proc = _cpu_cores[core].idle_proc;
    if(idle_proc != NULL) {
        idle_proc->info.state = WAIT;      // idle 进程平时挂起
    }

    proc_t* next = proc_get_next_ready();  // 从就绪队列取下一个进程
    if(next == NULL && idle_proc != NULL)
        next = idle_proc;                  // 没人可跑 → 跑 idle（空转）

    if(next != NULL) {
        next->info.state = RUNNING;
        proc_switch(ctx, next, false);     // ★切换过去
        return 0;
    }
    halt();                                // 连 idle 都没有 = 内核出大事了
}
```

`proc_get_next_ready()` 按优先级和轮转规则从队列里挑进程
（EwokOS 支持 `SYS_PROC_PRIORITY` 调整优先级）。

**谁来调用 `schedule()`？** 回顾第 06 章：每次定时器中断都会调用它。
所以调度发生在两个时机：
1. **时间片耗尽**（定时器中断，强制）；
2. **进程主动让出**：阻塞（等数据）、`SYS_YIELD`、退出。

**idle 进程**：每个核心有一个特殊进程，里面就是死循环休眠。
它是"永远有活可干"的保底，也是统计"CPU 空闲时间"的依据。

## 7.5 上下文切换：proc_switch 逐行理解

看 [proc.c](../../kernel/kernel/src/proc.c) 的 `proc_switch`（简化）：

```c
void proc_switch(context_t* ctx, proc_t* to, bool quick){
    proc_t* cproc = get_current_proc();     // 当前进程

    // ① 保存当前进程的寄存器现场
    memcpy(&cproc->ctx, ctx, sizeof(context_t));

    // ② 换页表（如果两个进程不共享内存空间）
    //    写 TTBR0 寄存器，从此"看到"的是新进程的内存世界
    if(cproc != to && cproc->space != to->space) {
        page_dir_entry_t *vm = to->space->vm;
        set_translation_table_base(V2P(vm));   // 第 05 章的页表切换！
    }

    // ③ 如果新进程有待处理的中断/信号/IPC 请求，
    //    把它的上下文"劫持"到对应的处理函数（7.7 节详解）
    ...

    // ④ 原进程若仍可运行，丢回就绪队列
    if(cproc->info.state == RUNNING) {
        cproc->info.state = READY;
        queue_push(&_ready_queue[cproc->info.core], cproc);
    }

    // ⑤ 返回后，异常出口用 to->ctx 恢复寄存器 —— 新进程开始运行
}
```

关键在第 ⑤ 步：`proc_switch` 是在异常处理路径里被调用的，
它把 `to->ctx` 放到恢复现场的位置，`eret` 一执行，
CPU 就带着新进程的寄存器和页表"醒来"了——
**对新进程而言，它只是从上次被暂停的那条指令继续执行**，完全无感。

## 7.6 进程的一生：生命在繁殖

7.2 节的第一个进程是内核亲手造的特殊个案。常态下，进程像生命一样
**由已有进程繁殖**：`fork` 生出一个和自己一样的孩子，`exec` 让孩子变成
另一个人，`exit` 谢幕。对应实验主线的"第 8 套代码"。

### fork：进程裂变繁殖

`fork()` 的语义简单到粗暴：**复制自己，得到一个一模一样的副本**。
代码、数据、堆栈、打开的文件、执行到哪一行——全部一样。
连"下一条要执行的指令"都一样。那父子怎么区分？

约定藏在**返回值**里：`fork()` 在父子进程里各返回一次——

```c
int32_t pid = fork();
if(pid == 0) {
    // 我是孩子：fork() 返回 0
} else if(pid > 0) {
    // 我是父亲：fork() 返回孩子的 pid
} else {
    // 负数：创建失败
}
```

同一个函数，两个世界，靠返回值分身份。这是操作系统史上最著名的设计之一。

### 分道扬镳的父子关系

裂变完成后，父子就是**两个完全独立的进程**：

- 各有一份寄存器现场，各自被调度，谁也不等谁；
- 各自独立的内存视图——之后一方写自己的变量，另一方完全不受影响；
- 联系只剩两条血缘记录：孩子的 `parent` 指向父亲（为了收尸与信号传递），
  父亲的 `children` 挂着孩子。

典型的分工模式是"父亲等结果、孩子干活"，或配合 `exec`——
孩子一出生就变身成新程序（第 11 章的 shell 执行命令就是这个套路：
fork 出一个孩子，孩子立刻 exec 成 `ls`，父亲 `wait` 收尸）。

### fork 的实现方法：写时复制

朴素做法是把父亲的全部内存复制一份给孩子——慢，而且浪费：
很多孩子一出生就 `exec`，刚复制的内存整个扔掉。

EwokOS 用**写时复制（Copy-on-Write，CoW）**，[proc.c](../../kernel/kernel/src/proc.c)
中的 `kfork()` 流程：

```
① 进程表找空槽，分配新 pid，记好父子关系
② 复制父亲的页表结构——但只复制"表"，不动"页"：
   父子页表项指向同一批物理页，同时把双方页表项的
   权限改为只读
③ 物理页引用计数 +1（第 05 章的 _pages_ref）
④ 孩子的 ctx 直接拷父亲的，只把 fork 的返回值改成 0
⑤ 孩子进就绪队列，等调度
```

此时父子真的"一模一样"，共享全部物理内存。分裂发生在第一次写入：

```
子进程写某一页 → 页表项是只读 → 触发异常 → 内核发现是 CoW 页
→ 分配一个新物理页、拷贝内容、把写方的页表项换成新页并恢复可写
→ 返回用户态，写操作重新执行，成功
```

**复制被推迟到真正需要的那一刻，而且只复制被写的那一页**。
对程序来说一切无感；对内核来说，一次 `fork` 的开销从
"复制几十 MB 内存"降到"复制几页页表"。

> 顺带理解：`_pages_ref` 引用计数在这里还防止内存泄漏——
> 任何一方退出释放内存时，引用计数大于 1 的页不能真正释放，只减计数。

### exec：加载新程序

`SYS_EXEC_ELF` 系统调用把当前进程的内存空间替换为一个
**ELF 文件**（可执行文件的标准格式）的内容：
解析 ELF 头 → 把代码段、数据段映射进进程内存 → 把入口地址写进 `ctx.pc`。
shell 执行命令就是 `fork()` + `exec()` 的组合（第 11 章）。

### exit：谢幕

进程退出时不能立即销毁——父进程可能还要读它的退出码。
所以先变 **ZOMBIE**，保留最小信息；父进程 `wait()` 收尸后才释放。
若父进程先死了，子进程会被过继给 `init`，由 init 负责收尸
（这就是 init 永远存在的原因之一）。

## 7.7 微内核的高级技巧：上下文劫持

`proc_switch` 的第 ③ 步藏着一个贯穿全书的机制。当内核需要让某个进程
"插队执行"一段代码时（比如：硬件中断来了要叫驱动进程处理、
IPC 请求到达要叫服务端处理），它不唤醒新线程，而是**直接改写该进程
即将恢复的上下文**：

```c
// 以"给进程注入一次硬件中断处理"为例：
to->ctx.gpr[0] = interrupt_no;              // 参数1：中断号
to->ctx.gpr[1] = data;                      // 参数2：附加数据
to->ctx.pc = to->ctx.lr = entry;            // ★程序计数器指向处理函数
to->ctx.sp = 新分配的栈;                     // 给处理函数一个干净的栈
```

该进程下次被调度时，会"莫名其妙"地从 `entry` 函数开始执行，
就好像它自己调用了一次 `entry(interrupt_no, data)`。
处理完（调用 `SYS_INTR_END`/`SYS_IPC_END`）后，
内核再把它保存的原始上下文还原回去——进程继续原来的工作，无感无痕。

**微内核的全部驱动和服务器都靠这个机制被"叫醒"**。
第 09 章讲 IPC 时你会再次见到它。

## 7.8 多核（SMP）

树莓派 3B/4B 有 4 个核。EwokOS 的做法：

- 每个核一条就绪队列、一个 idle 进程；
- 核间用 **IPI（核间中断）** 互相踢一脚："喂，有新任务了/该调度了"；
- 共享数据结构用自旋锁保护（`mcore_lock`）。

内核启动日志里 `kernel: start cores ... 0 1 2 3` 就是主核把 3 个从核唤醒的过程。

## 7.9 动手练习

1. 启动系统运行 `ps`，对照 7.3 节的状态机解释每个进程的状态；
2. 运行两个 `sleep 10` 后台任务 + 一个 `graphbench` 之类的忙任务，
   观察它们"同时"运行——每秒 1024 次切换下毫无破绽；
3. 阅读 [schedule.c](../../kernel/kernel/src/schedule.c) 全文（只有 35 行），
   然后在 [proc.c](../../kernel/kernel/src/proc.c) 中定位 `proc_switch`，
   找到"保存现场 / 换页表 / 放回队列"三步。

## 7.10 本章小结

- 进程三要素 = 身份信息 + 内存空间 + 寄存器现场（`proc_t`）；
- 第一个进程由内核六步工序造出（load_init_proc），之后的进程都由已有进程繁殖；
- 状态机：READY → RUNNING → WAIT/ZOMBIE → 释放；
- 调度 = 从就绪队列取下一个进程；抢占由定时器中断触发；
- 上下文切换 = 保存旧 `ctx`、换页表、恢复新 `ctx`、`eret`；
- fork 用写时复制，exec 换掉整个内存空间，exit 先变僵尸；
- 微内核用"上下文劫持"把中断/IPC 请求注入目标进程执行。
